## 1. 要点

1. **物理 RAM で最大の固定費は CUDA コンテキスト（約 2.6GB）**。import は約 0.7〜0.8GB。モデルを 1 つも読む前に、**約 3.4GB の物理 RAM**を消費する [実測]
2. 従来使っていた `private`（commit 量）は**物理消費を過大評価する**。`import numpy` だけで private は約 780MB 増えるが RSS は増えない（OpenBLAS の予約）[実測]。以降、空き RAM の判定には物理消費（`available` の低下量と RSS 増加の大きい方）、commit 余裕の判定には private を使う
3. **DiT の GPU 直接ロードは、`torch_cpu.dll` のアクセス違反（0xC0000005）で失敗した**。物理 RAM は 4.3GB 以上を維持しており、メモリ中断ではない [実測]
4. クラッシュと同時に、**プロセスの commit が 6.5GB → 20.3GB へ約 1 秒で急増**した。開始前のシステム commit 余裕は 16.3GB で、急増分（+13.8GB）が余裕を超えていた。**commit 上限の超過が有力な原因**だが、確定ではない [推定]
5. 事前確認は commit の消費を 6.98GB と見積もっていたが、実際は 20.3GB に達した。**見積りが誤っていた**。許可条件を観測値で修正した（§6）

## 4. クラッシュの原因分析

状況証拠 [推定]:

- 失敗は `torch_cpu.dll`（CPU 側）で起き、`device_map` による GPU 直接ロードの開始直後（約 5 秒後）。従来の経路（CPU に実体化してから GPU へ転送）は本番で成功していた
- 直前に commit が 6.5GB → 20.3GB へ急増。開始前の commit 余裕は 16.3GB で、CUDA コンテキスト後の残りは約 9.8GB。急増分（+13.8GB）はこれを**約 4GB 超過**する
- commit が尽きると、確保失敗を検査しないネイティブコードがアクセス違反を起こしうる
- VRAM の確保と commit の急増が同時に起きた。Windows（WDDM）では GPU メモリの割り当てがプロセスの commit に計上される挙動が有力。急増後に残った +4.7GB は DiT の VRAM 4.5GB に相当する

**確定していない点**: commit 余裕は 1 秒間隔のテレメトリに入っておらず、クラッシュ時の実際の余裕は未測定（今回の不足）。ほかに、safetensors の CUDA 直接読み込み、flash attention、`trust_remote_code` モデルとの組み合わせによるバグの可能性が残る。原因の確定には、commit 余裕の記録と faulthandler によるスタックが要る（実装済み。§7）。

commit 上限が実際には動的（ページファイルの自動拡張）であり、上限は 93.8〜96.2GB の範囲で変動していた。上限超過の挙動は単純ではない。

システム commit の内訳（読み取りのみ）: 使用 約 77GB。プロセスの private 合計は 約 59GB で、Chrome 13.4GB（101 プロセス）、`backgroundTaskHost` **10.3GB（581 プロセス、物理 0）**、他プロジェクトの python 8.1GB、WSL 3.7GB、claude 3.5GB など。**いずれも停止していない**。

## 6. 許可条件の修正（実装済み、安全下限 3GB は引き下げていない）

- 空き RAM の判定: 物理消費の実測値 + 3GB。DiT 段階の物理上限を 0.6 → **1.0GB** に引き上げ（観測 0.86GB を反映）
- commit 余裕の判定: private ベース + **観測した DiT 段階の急増（+13.8GB）** + 4GB。現状の commit 余裕（16〜19.6GB）では **C は許可されない**（必要約 24.2GB）。前回の失敗の再現防止
- 空き VRAM の判定: DiT 4,570MiB + CUDA コンテキスト 861MiB（実測）+ 512MiB = 5,943MiB
- **commit 余裕の監視を追加**: 1 秒間隔のテレメトリに `commit_headroom_gb` を記録し、下限 3GB を 3 回連続で下回ったら所有プロセスのみ停止（外側の監視）。子プロセスの自己監視（0.25 秒）にも同じ下限を追加
- ただし、commit の急増は 1 秒未満で起きるため、**事後の監視では防げない**。急増を見込んだ事前の許可条件（上記）が本質的な防御になる

## 8. 候補 H（LM を GPU に常駐）の実現可能性

実測した VRAM（GPU 全体 8,188MiB）:

| 項目 | MiB |
|---|---|
| 他アプリの使用（常時） | 1,769 |
| CUDA コンテキスト（実測） | 861 |
| **実際に利用可能な VRAM** | **約 5,558** |
| DiT bf16（現状の重み） | 4,570 → 残り **約 988** |
| DiT INT8（**未確認**。見込み 約 2,460〜3,070） | → 残り **約 2,490〜3,100** |

評価:

- **DiT が bf16 のままでは不可能**（残り 988MiB < LM 約 1,311MiB）。前回 VAE が CPU へ落ちた原因（空き VRAM 0）とも整合する
- **INT8 が実機で動いた場合に限り、可能性あり** [推定]。LM（約 1,311MiB + 生成時の KV キャッシュ [未測定]）を常駐させると残りは約 1,200〜1,800MiB。VAE デコード（実効空き 512MiB 以上が必要。タイルの一時領域は未測定）は足りる見込みだが、Text Encoder の GPU 転送（約 1,150MiB）は**ほぼ余裕がない**
- RAM 削減見込み: LM の物理 約 1.46GB
- 結論: **現時点では判断できない。INT8 の実機動作（D）の確認が前提**。D は C の成功が前提で、C は上記のクラッシュ原因が解決するまで進められない

## 9. RAM の見通し（実測に基づく訂正）

物理 RAM のベースラインは **3.4GB**（import 0.8 + CUDA 2.6）[実測]。低ピーク方式の全モデル初期化後の常駐は、VAE 0.34 + Text Encoder 1.28 + LM 1.46 を加えて **約 6.5GB**、DiT 段階の一時分を含めて 約 6.5〜7.4GB [推定]。

| 起動前の空き | 低ピーク方式のみ | + 候補 H |
|---|---|---|
| 8GB | 残り 約 0.6〜1.5GB（下限 3GB を満たさない） | 残り 約 2.1〜3.0GB（ぎりぎり） |
| 6GB | 不可 | 不可 |

これは前回の見積り（残り 2GB 台）より**厳しい**。CUDA コンテキストの 2.6GB を減らす手段が見つからない限り、8GB 基準の達成は候補 H と INT8 に依存する。
