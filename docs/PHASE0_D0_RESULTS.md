## 1. 要点

1. **`0xC0000005` は再発しなかった。** `safe_open(device="cuda:0")` で 256MB の合成ファイルを 1 テンソルずつ GPU へ読み込む手順は、この環境で正常に完了し、値は CPU の参照と完全に一致した（小さなテンソル・256MB の規模では、safetensors の CUDA 直接読み込み自体は壊れていない）
2. **commit の計上機構を 2 つとも実測で確認した。**
   - **M1（ファイルマッピング）**: `safe_open` 1 回（1 マッピング）ごとに、ファイルサイズ分の commit。3 重に開くと 3 倍（3.02 倍）
   - **M2（VRAM の確保）**: `cudaMalloc` 相当（`torch.empty` on CUDA）ごとに、確保サイズ分の commit が**ほぼ 1 対 1**（0.83〜1.07 倍）で計上され、解放（`empty_cache`）で戻る
3. **`safe_open(device="cuda")` の commit は約 2 倍**（マッピング 1 倍 + VRAM 1 倍）。先に私が出した 2.9 倍は、**検証コード自身の GPU 一時領域（+225MB）を含んでいた**ため訂正する（§4）
4. **warmup 相当の確保を挟んでも commit は約 2.2 倍で、挟まないときと変わらない**。warmup は VRAM の確保を前倒しするだけで、ピークの commit は増減しない。**`--disable-warmup`（D2）は commit の急増を減らさない見込み**
5. **前回の DiT の 3 倍（13.8GB）のうち、D0 で説明できたのは 2 倍分（マッピング + VRAM）まで**。残りの 1 倍（約 4.6GB）の出どころは**未特定**
6. **新たな大きな発見: CUDA 初期化のホスト側コストは import に依存する。** torch のみを import した後の CUDA 初期化は **+306MB（private）/ 物理 約 0.1〜0.3GB** だったのに対し、`acestep.handler` を import した後（前回の B2）は **+3,987MB / 物理 約 2.6GB** だった。前回の「CUDA コンテキストが 2.6GB」は**誤りで、CUDA 自体ではなく、import した何かが原因**。原因を切り分けて避けられれば、最大で物理 約 2.8GB・commit 約 3.7GB を削れる可能性がある

## 4. 前回の報告の訂正

- **「`safe_open(device="cuda")` が約 2.9 倍」は誤り**。D0 の検証（`.float()` で全要素の有限性を確認）が GPU に一時領域を作り、private・VRAM を増やしていた。本来は **約 2 倍**
- **「CUDA コンテキストの物理 2.6GB」は誤り**。torch のみの CUDA 初期化は +306MB。前回の B2 の +3,987MB は、import した何かとの組み合わせ（§3.1）

- **D0b による追記**: 上記の「import した何か」は、`acestep.handler` が eager に読み込む学習用ライブラリ（peft / lycoris 等）を含む import 連鎖だった。CUDA を先に初期化すると増分は +306MB に留まる。詳細は [PHASE0_IMPORT_MEMORY_INVESTIGATION.md](PHASE0_IMPORT_MEMORY_INVESTIGATION.md)（直接機構は未特定、最初の GPU 処理・実生成での効果は未検証）

## 5. private bytes とシステム commit の関係（測定に基づく分析）

| 操作 | private 増分 | システム commit 増分 | 比 |
|---|---|---|---|
| CUDA 1GiB 確保 | +1,026MB | +1.003GB（1,027MB） | 1.00 |
| `safe_open` ×3（256MiB） | +769MB | +0.756GB（774MB） | 1.01 |
| `safe_open(cuda)` + 読み込み | +738MB（検証込み） | +0.728GB（745MB） | 1.01 |

- **このプロセスの private の増分は、システム commit の使用量の増分と 1 対 1（誤差 ±1%）**。private bytes は、このプロセスが他プロセスの commit を圧迫する量そのものを表す
- **メモリマップされたファイルの commit**: 1 マッピングごとに、ファイルサイズ分（256MiB → +256MB）が、読み出し（RSS の増加 +1MB）とは無関係に、`safe_open` を開いた時点で計上され、閉じた時点で戻る
- **VRAM の確保**: `torch.empty(device="cuda")` のサイズ分が、確保時点で計上され、`empty_cache` で戻る。物理 RAM（RSS）は増えない
- したがって commit は「物理に載っているか」ではなく「確保・マップしたか」で決まる。物理 RAM に余裕があっても、commit は急に尽きうる
